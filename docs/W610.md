## Verified documentation

| Topic | Evidence | Implementation consequence |
|---|---|---|
| Transparent bridge | Current manual, p. 18, §4.1.1: transparent mode transports serial and WIFI/Ethernet data without analyzing it. | Treat the WebSocket payload as an opaque byte stream at this layer. |
| Serial configuration support | Current manual, p. 26, §4.3.1: baud rates from 300 to 460800; data bits 5–8; stop bits 1–2; parity None/Even/Odd. | 7 data bits, even parity, 1 stop bit, and 9600 baud are supported settings; configure the W610 itself. |
| Flow-control support | Current manual, p. 5, serial-port specifications: hardware RTS/CTS and software XON/XOFF are listed. | XON/XOFF bytes must remain data at the browser transport layer; FE1 owns later protocol interpretation. |
| Serial free framing | Current manual, p. 27, §4.3.2: packets can be split at an inter-byte interval threshold; a 10 ms test interval produced approximately 40–50 ms Wi-Fi→UART→Wi-Fi loopback delay. | WebSocket message boundaries are not protocol message boundaries. Buffer and parse the stream independently. |
| WebSocket server port | V1.0.1.01 manual, p. 16, §3.3.6: WebSocket occupies W610 port 8000 and permits up to eight clients. | Port 8000 is a candidate, but the URL path still requires verification. |
| One serial resource | V1.0.1.01 manual, p. 16, §3.3.6: eight WebSocket clients can connect. | The application acquires a cross-tab exclusive browser lock; Milestone 1 cannot prevent unrelated clients outside this app. |

The current manual contains copy-editing references to `USR-DR404` in sections describing free framing. The W610 title, product section, and serial capabilities are clear, but those timing statements should be confirmed with the exact W610 firmware before relying on them.

## Deliberately unverified

The official W610 manuals found above do **not** specify:

- the actual WebSocket URL path behind `/websocket.html`;
- whether the stock page negotiates a subprotocol;
- whether serial bytes arrive in binary or text WebSocket frames;
- the text-frame character-to-byte mapping;
- whether every 7-bit control byte survives the stock page and firmware unchanged;
- downstream serial parity or framing errors visible to the browser;
- whether short FE1 request/response packets incur unacceptable latency.

The target W610 at `10.10.100.254` was not reachable from the build machine, so its stock `/websocket.html` could not be inspected. The console therefore exposes host, port, path, and timeout. It marks `ws://10.10.100.254:8000/` as an endpoint candidate rather than a verified endpoint.

## Implemented transport behavior

- Outbound data is copied to a `Uint8Array` and sent as a binary WebSocket frame.
- Incoming `ArrayBuffer` and `Blob` values are copied to exact byte arrays.
- Incoming text is encoded with UTF-8. This preserves code points `0x00`–`0x7F`, but UTF-8 is not a safe assumption for arbitrary binary file data; binary frames are required for hardware validation.
- Each WebSocket message is logged as one receive chunk.
- `ByteStreamBuffer` preserves arbitrary chunk boundaries, including split packets and multiple packets in one chunk.
- Connection loss transitions to `closed`, emits an unexpected-loss event, clears the incomplete stream, and does not reconnect.
- Reconnecting is an explicit operator action and creates a new socket with fresh per-connection counters.
- Outbound binary frames and all 7-bit received byte values are covered by browser tests.

## Required stock-page inspection

Before claiming W610 compatibility:

1. Open `http://10.10.100.254/websocket.html` while connected to the W610 network.
2. Use browser developer tools to inspect the page source and the `new WebSocket(...)` call.
3. Record the exact URL, path, subprotocol, and message handlers.
4. Connect the app to that URL and send `00 01 02 03 04 06 11 13 15 17 7F`.
5. Capture both the browser WebSocket frames and a PC serial-side trace.
6. Repeat with a loopback and a small real TNC response before implementing FE1 timing.
